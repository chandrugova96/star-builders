# First free deployment — Render + MongoDB Atlas

## Prepared architecture

One Render **Free Web Service** runs the existing Express API and serves the React production build. MongoDB remains in Atlas. Both the UI and `/api` use the same HTTPS origin, so no frontend API URL, Vite environment variable or second hosting service is required. Local development still uses Vite and API port 4000.

The root `render.yaml` declares `plan: free`, Node 22, Singapore region, the build/start commands and a database-readiness health check. It creates no Render database, disk, worker or other paid service. Confirm the existing Atlas cluster is the Free/M0 tier if the entire deployment must be free; its current tier has not been inspected by this agent.

Status: local deployment preparation is complete. This document is not evidence of a live deployment. Publishing requires access to the owner's Git repository, Render account and Atlas network settings. No real database credentials are included in the deployment files.

## Deploy using the Blueprint

1. Put this project in a **private GitHub repository** with `render.yaml` at its root. Include both package lockfiles and source/assets. Keep `.env`, `node_modules`, `dist`, test output and real personal data out of Git. The supplied `.gitignore` already excludes generated files and environment files, while allowing `.env.example`.
2. Sign in at [Render](https://dashboard.render.com/) using the Git provider that owns the repository.
3. Choose **New → Blueprint**, connect that repository and select the branch containing these files. Use the root `render.yaml`; do not set a root directory of `backend` or `frontend`.
4. Confirm the service's compute plan is **Free** before creating it. The service name may need to be changed if already taken. The initial region is Singapore; adjust it to the Atlas region if appropriate and available.
5. Enter `MONGODB_URI` directly into Render's secret/environment field when prompted. Use the intended Atlas database containing the already-created Admin. Do not paste it into Git, a screenshot or chat. `JWT_SECRET` is generated by Render through the Blueprint.
6. In the Render service, open **Connect → Outbound** and copy its outbound CIDR ranges. Add those ranges to Atlas **Network Access → IP Access List**, keeping any local development access you still need. Allowlisting every address (`0.0.0.0/0`) is unnecessary. If the first deployment fails before the IP ranges are allowed, update Atlas and redeploy.
7. Wait for the deployment to show **Live**. Open the exact HTTPS URL assigned by Render. Sign in with the existing Admin account; this deployment does not create or reset any user.
8. Verify `/api/health/ready` returns `ready`; refresh `/attendance` and `/weekly-payroll` directly; confirm the logo/background load; then check the real Admin/Supervisor flow. Use intentional test records rather than posting accidental salary payments. Database writes target whichever database is in the supplied URI.

A newly generated JWT secret invalidates tokens signed by a different local/deployed secret. Signing in again issues a valid one-day token. Keep the generated deployed secret stable across redeploys unless deliberately rotating it.

## Manual Web Service settings (alternative)

Use **New → Web Service**, connect the private repository, leave Root Directory blank, and enter:

| Setting | Value |
|---|---|
| Runtime | Node |
| Instance | **Free** |
| Region | Singapore, or an appropriate available region near Atlas |
| Build command | `npm run deploy:build` |
| Start command | `npm run deploy:start` |
| Health check path | `/api/health/ready` |

Environment variables:

| Variable | Value |
|---|---|
| NODE_VERSION | `22` |
| NODE_ENV | `production` |
| HOST | `0.0.0.0` |
| SERVE_FRONTEND | `true` |
| TRUST_PROXY | `1` — only for Render's trusted ingress |
| MONGODB_URI | Atlas URI, entered privately in Render |
| JWT_SECRET | A randomly generated secret of at least 32 characters |

Render supplies `PORT` and `RENDER_EXTERNAL_URL`. Do not override `PORT` with localhost assumptions. Leave `CORS_ORIGINS` unset for the default Render URL; the API derives the exact allowed origin from `RENDER_EXTERNAL_URL`. If adding a custom domain, set `CORS_ORIGINS` to a comma-separated list of exact HTTPS origins (no paths or trailing slash), including any Render URL you still use.

Do not copy the entire local `.env` into Render: its localhost HOST/CORS settings are development defaults. Database/JWT secrets belong only in backend environment variables, never frontend `VITE_*` variables.

## What changed

- `backend/src/lib/frontend.ts`: serve only `frontend/dist`, with browser-route fallback. Missing assets and dotfiles stay 404.
- `backend/src/app.ts`: optional production frontend mounting, bounded trusted-proxy setting, API 404s stay JSON before SPA fallback.
- `backend/src/config/env.ts`: validated SERVE_FRONTEND/TRUST_PROXY and canonical Render-origin fallback.
- `backend/src/server.ts`: enable built-frontend serving when configured, preserving normal API-only local development.
- Root `package.json`: reproducible deployment build and start aliases. Builds explicitly include TypeScript/Vite development dependencies even under NODE_ENV=production.
- `render.yaml`: one Free service, generated JWT secret, private MongoDB URI input, no paid database.
- `backend/.env.example`, READMEs/project/development docs and deployment regression tests.

`frontend/vite.config.ts` and the UI/API client remain unchanged. Its localhost proxy is used only by Vite development/preview; the deployed Express process serves `/api` directly. Do not run Vite's development or preview server as the production server.

## Free-tier limits

Render's free service sleeps after 15 minutes without inbound traffic. Waking can take around a minute; Render may show a loading page first. It includes a workspace-level monthly allowance of 750 instance hours and has bandwidth/build quotas. Exceeding usage can suspend services/builds, or incur charges if a payment method is configured. Keep the service on Free, review usage/spend limits and avoid enabling paid add-ons. Render describes Free as intended for preview/testing rather than dependable production hosting.

The service filesystem is temporary. This app stores records in Atlas, so sleep/redeploy does not erase those records. Do not rely on local files for database backups. Atlas backup subscription options can have separate costs; backups are not configured by this deployment. Establish a backup/restore process and appropriate availability before relying on this installation for regular payroll.

## Checks and troubleshooting

- Build failure: verify the root build command, both committed lockfiles, Node version, and dependency installation. Do not omit build-time dev dependencies.
- Port not detected: verify HOST=0.0.0.0 and allow Render to supply PORT.
- Startup/readiness failure: verify the URI's intended database, database user permissions, Render outbound allowlist and Atlas availability. Startup also ensures unique business indexes; conflicting historical records can stop it.
- Frontend build missing: build the complete repository and enable SERVE_FRONTEND only after `npm run build` succeeds.
- Login CORS failure: remove local CORS_ORIGINS or set the exact deployed origin(s).
- Site seems slow after inactivity: allow the free service to wake before retrying. There is no automatic financial retry/repost on timeouts.

Local checks cover deep links, built assets, hidden files, API isolation, CORS, proxy-aware login throttling and environment validation. Build artifacts and database scenarios are tested independently; a live Render deployment still needs to be verified after account/repository access is available.
